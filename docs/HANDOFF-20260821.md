- 目标是逐步弃用 vendor 内核，最终使用主线内核运行 W132D。
- USB2、USB3、有线网口、WiFi 和蓝牙已经通过当前主线镜像的实机测试，后续 HDMI 工作不得回归这些功能。

## HDMI 早期尝试内容（历史）

- 用 RK3568 VOP2 和 RK3328 DesignWare HDMI/INNO PHY 作为兼容匹配，暴露 RK3528 的实际寄存器地址。
- 将 PHY 输出时钟名修正为 RK3528 CRU 使用的 `clk_hdmiphy_pixel_io`。
- 按 vendor DT 加入 `hpd-gpios = <&gpio0 RK_PA2 GPIO_ACTIVE_HIGH>;`。
- 修正过 VOP 输出端点和 HDMI 输入端点的连接关系。

这些改动只能让 DRM 控制器完成 probe，不能证明 RK3528 的 VOP、HDMI glue、PHY 和 HPD/EDID 链路寄存器兼容。当前没有 HPD 变化、EDID 或显示模式，显示器不会被唤起，最终状态仍为 `disconnected`。

## HDMI 早期结论（已被后续结果更新）

Linux 7.1 当前只有通用 DRM/DesignWare HDMI 框架，缺少完整的 RK3528 VOP、HDMI glue 和 INNO HDMI PHY 主线匹配及寄存器数据。现有板级 DTS 使用 RK3568/RK3328 fallback，只能让设备 probe，不能证明显示链路可用。

后续必须先提取 W132D Android 9/vendor DTB，并核对 VOP 三段寄存器、IOMMU、HDMI GRF、双中断、四个时钟、PHY 初始化、HPD 和 pinctrl；再移植 RK3528 专用驱动数据。不要继续通过单独替换 compatible、强制 HPD 或 dummy regulator 反复试错。

vendor 6.1 上已经验证过的 `Cluster0` primary plane、`plane-mask = 0x05` 和 `esmart_lb_mode = 3` 只作为后续 2560x1440 画面完整性测试依据。当前主线首先要解决的是 CRTC/HPD/EDID 链路完全没有建立的问题。

主线 HDMI 的阶段性验收顺序固定为：接入 HDMI 后启动、1920x1080@60、确认 connector/EDID/CRTC、再测试 2560x1440，最后测试热插拔和待机唤醒。

## 无线适配记录

无线硬件是 UWE5622（固件芯片 ID `0x56630001`），原机使用 WCN/SDIO 方案：

- SDIO1：`mmc@ffc20000`，4-bit、non-removable、`cap-sdio-irq`，vendor 方案使用 SDR104。
- GPIO3_A2：WCN 电源/复位序列，由 `mmc-pwrseq-simple` 持有。
- GPIO3_A3：WCN/SDIO 外部数据中断。
- GPIO3_A4：WCN/BT enable/reset。
- GPIO3_C1：BT wake-host。

蓝牙数据不是普通 UART HCI；vendor 驱动通过 WCN SDIO 通道暴露 `ttyBT`，再由用户态 HCI 初始化程序交给 BlueZ。当前主线移植已经按这一路径完成，WiFi 扫描/连接/吞吐和蓝牙控制器基本功能均已通过实机测试。不能退回仅启用 `uart2` 或直接运行通用 `hciattach` 的方案。

## HDMI HPD GPIO evidence and RK3528 workaround (2026-08-22)

The latest hardware capture narrowed the failure to the RK3528 HPD path rather
than the cable, EDID mode, or the invalid GRF read attempted during diagnosis.
With the cable disconnected, connected, and disconnected again, the device
reported the same values:

```text
busybox devmem 0xff610000 32  -> 0x00000000  (GPIO0 data)
busybox devmem 0xff610008 32  -> 0x00000000  (GPIO0 direction)
busybox devmem 0xff610070 32  -> 0x00000038  (GPIO0 EXT_PORT; PA2 is low)
busybox devmem 0xff610078 32  -> 0x0101157C  (GPIO version)
```

`busybox devmem 0xff3c0014 32` returned `Bus error`. That address is not a
valid readable HDMI GRF register in this mapping and must not be used as
evidence for HDMI state.

The debug pinmux/gpio output was:

```text
pin 2 (gpio0-2): ff8d0000.hdmi gpio0:514 function hdmi group hdmi-pins
gpio-2 ( |hpd ) in lo
```

The mainline DTS selected the common `hdmi-pins` group, which muxes PA2 to
HDMI function 1 while also passing PA2 as `hpd-gpios`. This leaves the GPIO
consumer unable to observe the physical HPD line. The mainline glue also had
only a partial vendor workaround: it lacked the RK3528 `SNKDET_SEL` bit, the
GPIO0_A2 output-data input-enable write, and a rising/falling GPIO HPD IRQ.

Vendor 6.1 commit `5e211fd0670b` confirms the intended sequence: keep PA2 in
GPIO mode, set GPIO0_A2 data bit 2 to enable its input, select the GPIO HPD
source through VO-GRF `0x60014` bit 6, mirror the GPIO level to SNKDET bit 5,
and update that bit on both HPD edges. The current port follows that sequence
in the mainline glue and uses a board-local pin group containing CEC/SCL/SDA
only. This is an HPD/EDID bring-up fix; it does not yet claim that the
incomplete RK3528 VOP2 descriptor or 2560x1440 modesetting is solved.

## HDMI single-clock diagnostic image (2026-08-22 21:51 UTC+8)

- The 241.5 MHz PHY entry was accepted and the HDMI encoder logged
  `mode_set ... ret=0`, but the monitor still flickered. This rules out the
